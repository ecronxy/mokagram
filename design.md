# Айдентика mokaGram

Этот документ описывает визуальный язык десктопного клиента и служит ориентиром для новых экранов и проверки существующих. Основа — существующий интерфейс Моки: мягкие скругления, спокойные поверхности, заметный акцент и плотная, удобная для рабочего стола компоновка. Material 3 используется как направление для форм и состояний; полное соответствие спецификации пока не заявляется.

Документ различает **текущее поведение** и **направление развития**. Значения ниже относятся к логическим единицам интерфейса и не требуют фиксированного размера окна.

## Принципы

- Содержание важнее декоративных эффектов: в списках на первом плане название, затем пояснение и дополнительные данные.
- Скруглённые поверхности объединяют связанные элементы; между независимыми группами оставляем воздух.
- Акцентный цвет обозначает выбор и основные действия. Вторичный текст, время и подписи визуально тише основного текста.
- Состояния должны читаться без догадок: выбранное, наведённое, недоступное и воспроизводимое состояние различимы.
- Тема пользователя определяет цвета. Нельзя считать белый фон или синий акцент постоянными для всех тем.
- Интерфейс остаётся пригодным для клавиатуры, масштабирования, локализации и RTL; цвет не должен быть единственным признаком важного состояния.

## Цвет

Используем семантические цвета существующей палитры, а не фиксированные значения в отдельных экранах. Примеры ниже — значения по умолчанию из `Telegram/lib_ui/ui/colors.palette`, а не обязательная палитра всех тем.

| Роль | Токен | Значение по умолчанию |
| --- | --- | --- |
| Поверхность | `windowBg` | `#ffffff` |
| Основной текст | `windowFg` | `#000000` |
| Вторичный текст | `windowSubTextFg` | `#999999` |
| Поверхность при наведении | `windowBgOver` | `#f1f1f1` |
| Акцентная заливка | `windowBgActive` | `#40a7e3` |
| Текст на акцентной заливке | `windowFgActive` | `#ffffff` |
| Акцентный текст | `windowActiveTextFg` | `#168acd` |
| Фон предупреждающей кнопки | `attentionButtonBgOver` | `#fcdfde` |

При проверке светлой, тёмной и пользовательских тем отдельно проверяем читаемость текста, границ и состояний. Цвета на схемах иллюстративны: они не заменяют проверку в приложении.

## Форма и размеры

| Элемент | Текущее правило |
| --- | --- |
| Окно из `BoxParts` | Радиус 28 |
| Карточка из `BoxParts` | Радиус до 22, ограничен половиной высоты |
| Круглая кнопка заголовка | 36 × 36 |
| Кнопка-пилюля диалога | Высота 40, полное скругление |
| Поле карточки | Минимальная высота 44 |
| Переключатель Моки | 40 × 24; анимация изменения 200 мс |

Это не универсальные размеры каждого виджета приложения: у существующих экранов есть отличия. Общие детали окон находятся в [`mokagram_box_parts.h`](Telegram/SourceFiles/mokagram/ui/mokagram_box_parts.h) и [`mokagram_box_parts.cpp`](Telegram/SourceFiles/mokagram/ui/mokagram_box_parts.cpp). Отступы и радиусы новых экранов следует брать из общих правил там, где их смысл совпадает, а исключения документировать рядом с экраном.

## Состояния и взаимодействие

Для интерактивных элементов учитываем обычное состояние, наведение, нажатие, фокус клавиатуры, недоступность и выбранное значение. Визуальное состояние должно соответствовать действительному поведению элемента. Анимация помогает увидеть смену состояния и не должна задерживать действие; при отключённой анимации результат должен оставаться понятным.

В настройках переключатель может быть индикатором значения, а клик обрабатывает вся строка. В плагинах переключатель обрабатывает клик сам. Если система плагинов отключена, индикатор показывает выключенное состояние, сохраняя выбранное пользователем значение. Эти сценарии используют общую отрисовку, но различаются управлением.

## Музыкальное окно

Референс экрана из чатов: [схема музыкального окна](docs/design/moka-music.svg). Общие формы и цвета показаны на [листе элементов](docs/design/moka-identity.svg). Обе схемы вручную составлены по коду и референсу; они не являются снимками работающего приложения.

Текущее устройство экрана:

- **Шапка:** закрытие слева, название по центру, переход к очереди справа.
- **Поиск:** поле высотой 44 со скруглённым фоном; текст подсказки соответствует выбранному источнику.
- **Источник:** сегментированный переключатель SoundCloud / чаты высотой 40. Выбранная часть перемещается с анимацией 220 мс; на экране SoundCloud используется также выбор треков или альбомов.
- **Выбор чата:** отдельное действие высотой 36, показывается для поиска по чатам.
- **Список:** обложка 56 × 56 с радиусом 8; рядом название, вторичная строка и длительность. Воспроизводимая строка или строка под указателем получает фон с радиусом 12. Длинный текст не должен вытеснять длительность.

Реализация находится в [`mokagram_music_ui.cpp`](Telegram/SourceFiles/mokagram/music/mokagram_music_ui.cpp). Схема показывает только этот экран, а не все состояния музыкального плеера, очереди, загрузки и ошибок.

## Развитие системы

1. Использовать общие модули Моки для повторяющихся переключателей, карточек и кнопок. Экран должен задавать смысл и состояние, а общая реализация — одинаковое поведение и форму.
2. Пересмотреть группы настроек: сейчас разрывы карточек определяются неявными свойствами вложенных виджетов. Явный интерфейс группы упростит поддержку и проверку.
3. Сопоставить музыкальный экран с общими правилами, сохранив специфичные для него состояния воспроизведения и выбора источника. Не переносить детали только ради одинакового названия: сначала проверить, совпадают ли поведение и назначение.
4. Дополнить визуальный каталог фактическими снимками остальных экранов и состояний в светлой, тёмной и пользовательских темах. Существующие SVG — начало каталога, а не полная инвентаризация.

## Проверка изменений

Перед завершением визуального изменения проверить обычное и узкое окно, длинные локализованные строки, светлую и тёмную темы, наведение, нажатие, фокус, недоступное и выбранное состояния. Для музыкального окна дополнительно проверить пустую обложку, длинные названия, длительность, воспроизведение и переключение источника. По возможности сравнить результат в работающем приложении со схемами; схемы сами по себе не проверяют функциональность.
