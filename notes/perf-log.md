# mokaGram: журнал производительности

Замеры на release-сборке (ninja/moka-build, -O3), песочница `-workdir ~/dev/mokagram-data`, один аккаунт.
Логи старта: `grep "mokagram-perf" log.txt`. FPS: тумблер `lag.fps` в настройках (оверлей fps и 1% low за 5 с).

## Сценарий (повторять одинаково)
1. Холодный старт, один аккаунт: этапы `[mokagram-perf] run:` в логе, три прогона.
2. Скролл чата 50 000+ сообщений вверх и обратно, `lag.fps` включён.
3. Чат с 30+ анимированными премиум-эмодзи без действий, CPU% за 60 с (`pidstat -p PID 60 1`).
4. RSS после 10 минут простоя (`grep VmRSS /proc/PID/status`).

## Бенчмарк (база, до задач)
Старт, этапы `run()`: localStorage ~70 мс, moka-модули ~60 мс, **плагины 360-500 мс** (Python init при пустом каталоге плагинов), шрифты ~90 мс, создание окна 580-890 мс; всего 1.3-1.5 с.
Сценарии 2-4 требуют ручного участия владельца (большой чат, живой клиент): не измерены.

## Задача 2: ленивый движок плагинов
Каталог плагинов пуст: `Plugins::Start` выходит сразу, Python/хост (bwrap) не поднимаются, пока не установят плагин (`LoadFile`/`RecordInstall` стартуют движок сами). Старт вынесен из `Application::run()` на 300 мс после показа окна, `_started` стал атомарным, хуки и так выходят по `_started`/счётчикам фильтров до GIL.
- до: этап plugins на критическом пути 362-495 мс (total до окна 1.3-1.5 с)
- после, пусто: plugins на критическом пути 0 мс, отложенный вызов 1 мс, в логе нет "python"; total до окна 1.2-1.5 с (шум диска больше выигрыша, этап run() до окна: 304 мс против 582 мс по сумме этапов до fonts)
- после, с плагином (MOKAGRAM_PLUGINS_DIR с showcase.plugin): хост поднимается после окна, 456 мс, `plugins loaded` и START приходят как раньше.
Не проверено вручную: установка плагина из UI на живом клиенте и события в плагинах (нужен владелец).

## Задача 3: прекомпиляция питон-хелперов (пропущена, причина ниже)
Замер (python 3.14, release): compile() всех встраиваемых скриптов host 32 + sdk_api 34 + fw 30 + tl_names 7 + base_plugin 5 + tl 4 = ~111 мс; marshal.loads тех же объектов ~3 мс. kTlSchema (1.7 МБ) это данные, а не код: его не компилируют, только парсят.
Лог старта с плагином (после задачи 2, процесс-хост в bwrap): хост поднят и скрипты загружены 482 мс, `_moka_init` ещё +118 мс, итого ~600 мс. Кэш marshal убрал бы максимум ~110 мс из 600 (остальное: bwrap, запуск интерпретатора, парсинг схемы), то есть "кратного" падения критерий не даст.
Почему не делал: после задачи 2 это не на пути к первому кадру и только для пользователей с плагинами. Дочерний хост сидит в bwrap без доступа к каталогу данных клиента, значит кэш должен писаться и читаться через новый кадр протокола (marshal не передать как UTF-8 строку), плюс Qt-ресурс для исходников требует правки cmake и перегенерации проекта. Это меняет протокол хоста и сборку ради ~100 мс вне критического пути. Могу сделать отдельно, если нужно.
В коммит вошли лог-метки времени старта хоста (`[mokagram-perf] plugins: ...`).

## Задача 1: флаги сборки (изменено, НЕ собрано)
Каталог `cmake/` это сабмодуль cmake_helpers: правки лежат в рабочем дереве сабмодуля, копия патча в `patches/cmake.patch` (как `lib_ui.patch`).
- `MOKA_LTO` (ON по умолчанию): LTO для release теперь включается и без DESKTOP_APP_SPECIAL_TARGET (раньше только официальные сборки). Выключить: `-DMOKA_LTO=OFF`. GCC: INTERPROCEDURAL_OPTIMIZATION (-flto=auto, "thin" есть только у clang); MSVC: /GL + /LTCG.
- `MOKA_X86_64_V2` (ON): `-march=x86-64-v2` на linux x86_64. MSVC /arch:AVX не добавлял (задача говорит про линукс-билды, AVX на Windows режет старые CPU без тумблера).
- -O3 в release уже стоит (проверено по build.ninja); MSVC: /O2 по умолчанию CMake Release, добавлен /OPT:ICF к /OPT:REF.
- Не проверено: полная пересборка с LTO (часы и много RAM, занимает mokagram-build, нужно согласие владельца), размер бинаря, старт до/после, cmake-конфигурация на Windows/macOS. Текущий каталог сборки не переконфигурирован: флаги подхватятся при следующем запуске cmake.

## Задача 5: CPU в простое
- Ghost-таймер расписания: через `Perf::EconomyValue()` в экономном режиме (окно в фоне при включённом «Экономия в фоне», либо режим тостера) тик раз в 5 минут вместо 30 с, при выходе из экономии сразу `ApplySchedule()` и 30 с. Расписание в фоне может переключиться с задержкой до 5 минут.
- Эмодзи/стикеры в фоне уже останавливались через `EconomyValue()` (PowerSaving::SetForceAll). Другие moka-анимации читают `Perf::UserIsLooking()` (music UI).
- Лента (`mokagram_feed.cpp`): фоновых таймеров и опроса нет, это окно по запросу пользователя, останавливать нечего.
- Не измерено: CPU% за 60 с на чате с 30+ эмодзи (нужен живой чат). Сборка проходит, клиент стартует, метки старта в логе есть. Первая попытка замера промахнулась по pid, цифр нет.
